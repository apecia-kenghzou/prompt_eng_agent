## Testing Strategy & Tool Selection

### Test Pyramid Ratio Guidance ⭐ NEW

**Industry Standard**: Follow the 70:20:10 test pyramid distribution:

- **70% Unit Tests** - Fast (milliseconds), reliable, test business logic in isolation
- **20% Integration Tests** - Moderate speed (seconds), test component interactions (API + DB)
- **10% E2E Tests** - Slow (minutes), test critical user flows end-to-end

**Rationale**:
- Unit tests run 100x faster than E2E tests
- E2E tests are brittle (break on UI changes)
- Inverted pyramid (too many E2E tests) leads to 30+ minute CI builds

**Example Distribution for 1000 Tests**:
```
Unit Tests:        700 tests (~5 min)
Integration Tests: 200 tests (~3 min)
E2E Tests:         100 tests (~10 min)
Total CI Time:     ~18 min
```

**Anti-Pattern (Inverted Pyramid)**:
```
Unit Tests:        100 tests (~1 min)
Integration Tests: 200 tests (~3 min)
E2E Tests:         700 tests (~70 min)
Total CI Time:     ~74 min ❌ TOO SLOW
```

**Enforcement (Optional)**:
Add a CI linter to enforce the pyramid ratio:
```javascript
// jest.config.js or similar
if (e2eTestCount / totalTestCount > 0.15) {
  throw new Error(`E2E tests (${e2eTestCount}) exceed 15% of total (${totalTestCount}). Push logic to unit/integration tests.`)
}
```

### E2E Testing Frameworks
- **Cypress / Playwright**: Preferred for modern JavaScript applications. Choose for fast, reliable E2E tests with excellent debugging capabilities.
- **Selenium**: Choose for cross-browser testing scenarios that require support for a wide range of browsers or languages beyond JavaScript.

### API Testing
- **Postman**: Use for exploratory and manual API testing.
- **Automated API Tests**: Write API tests in code using libraries like `axios` or `requests`, integrated into the test runner (e.g., Jest, Pytest).

### Performance Testing
- **JMeter / K6**: Use for protocol-level performance testing to simulate heavy user loads.
- **Lighthouse**: Use for front-end performance analysis and auditing, integrated into the CI pipeline.

### Methodologies
- **BDD (Behavior-Driven Development)**: Write test cases in Gherkin syntax (`Given/When/Then`) that are understandable to both technical and non-technical stakeholders. These specifications should drive the implementation of E2E tests.
- **Shift-Left Testing**: Get involved early in the development cycle. Review requirements and design documents to identify potential issues before any code is written.

## QA Implementation Strategy

### Test Data Management

#### Core Principles
- **Data Creation**: Test data must be created programmatically before each test run (e.g., using API calls, database fixtures, or libraries like Faker.js). Do not rely on pre-existing data in the test environment.
- **Data Isolation**: Each test case should be responsible for creating the specific data it needs and should not depend on the state left by other tests.
- **Data Teardown**: All created test data must be cleaned up after the test suite completes to ensure a clean state for the next run.

#### PII Masking & GDPR Compliance ⭐ NEW

**Requirement**: When using production data in test environments, ALL Personally Identifiable Information (PII) must be masked to comply with GDPR Article 32 (pseudonymization).

**What to Mask**:
- **Email addresses**: `john.doe@example.com` → `user_12345@example.com`
- **Names**: `John Doe` → `Test User 12345`
- **Phone numbers**: `+1-555-0100` → `+1-555-0000`
- **Credit card numbers**: `4532-1234-5678-9010` → `4532-****-****-0000`
- **SSN/Tax IDs**: `123-45-6789` → `000-00-0000`
- **IP addresses**: `192.168.1.100` → `10.0.0.1`
- **Physical addresses**: Use generic addresses

**Tools for PII Masking**:

1. **Faker.js** (JavaScript/TypeScript) - Generate realistic fake data:
```javascript
const { faker } = require('@faker-js/faker');

// Mask user data from production snapshot
function maskUser(prodUser) {
  return {
    id: prodUser.id,  // Keep ID for referential integrity
    email: faker.internet.email(),
    firstName: faker.person.firstName(),
    lastName: faker.person.lastName(),
    phone: faker.phone.number(),
    address: faker.location.streetAddress(),
    createdAt: prodUser.createdAt,  // Keep timestamps
  };
}
```

2. **pg_anonymize** (PostgreSQL) - Database-level masking:
```sql
-- Create anonymization rules
CREATE EXTENSION IF NOT EXISTS pgcrypto;

UPDATE users
SET
  email = 'user_' || id || '@test.example.com',
  first_name = 'Test',
  last_name = 'User' || id,
  phone = '+1-555-' || LPAD(id::text, 4, '0'),
  ssn = '000-00-0000',
  ip_address = '10.0.0.' || (id % 255);
```

3. **AWS DMS with Transformation Rules** (Cloud-based):
```json
{
  "rule-type": "transformation",
  "rule-id": "mask-pii",
  "rule-action": "replace-with-default",
  "object-locator": {
    "schema-name": "public",
    "table-name": "users",
    "column-name": "email"
  },
  "value": "user@test.example.com"
}
```

**Log Scrubbing**:
Automatically redact PII from application logs before storing:
```javascript
// winston-pii-mask.js
const winston = require('winston');

const piiMaskFormat = winston.format((info) => {
  let message = info.message;

  // Mask credit card numbers
  message = message.replace(/\b\d{4}[\s-]?\d{4}[\s-]?\d{4}[\s-]?\d{4}\b/g, '****-****-****-****');

  // Mask email addresses
  message = message.replace(/\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Z|a-z]{2,}\b/g, '***@***.com');

  // Mask SSN
  message = message.replace(/\b\d{3}-\d{2}-\d{4}\b/g, '***-**-****');

  info.message = message;
  return info;
})();

const logger = winston.createLogger({
  format: winston.format.combine(
    piiMaskFormat,
    winston.format.json()
  ),
  transports: [new winston.transports.File({ filename: 'app.log' })],
});
```

- **Screenshots/Videos**: Store for 30 days, then auto-delete (may contain PII)
- **Test Reports**: Strip sensitive data before archiving (HTML reports with masked values)
- **Database Snapshots**: Re-mask monthly (data drift from new PII)

**Example Retention Script**:


### Test Environment Strategy

#### Environment Tiers
- **Local / Dev**: Developers run unit and integration tests locally before committing.
- **Staging / QA Environment**: A dedicated, production-like environment where full E2E and performance test suites are run. This environment is refreshed with sanitized production data via automated nightly refresh.

#### Test Environment Refresh Automation ⭐ NEW

**Problem**: Manual weekly refresh is error-prone and causes weekend outages.

**Solution**: Automated nightly refresh with validation and rollback.

**Refresh Procedure (Nightly at 2 AM UTC)**:

```bash
#!/bin/bash
# staging-refresh.sh - Automated test environment refresh

set -e  # Exit on any error

LOG_FILE="/var/log/staging-refresh.log"
SLACK_WEBHOOK="https://hooks.slack.com/services/YOUR/WEBHOOK"

log() {
  echo "[$(date +'%Y-%m-%d %H:%M:%S')] $1" | tee -a "$LOG_FILE"
}

notify_slack() {
  curl -X POST "$SLACK_WEBHOOK" -H 'Content-Type: application/json' \
    -d "{\"text\":\"$1\"}"
}

log "Starting staging environment refresh..."
notify_slack "🔄 Staging refresh STARTED"

# Step 1: Take snapshot of production DB (read replica)
log "Step 1: Creating snapshot from prod read replica..."
aws rds create-db-snapshot \
  --db-instance-identifier prod-db-read-replica \
  --db-snapshot-identifier staging-snapshot-$(date +%Y%m%d-%H%M%S)

# Wait for snapshot to complete
aws rds wait db-snapshot-completed \
  --db-snapshot-identifier staging-snapshot-$(date +%Y%m%d-%H%M%S)

log "Snapshot created successfully"

# Step 2: Restore snapshot to staging DB
log "Step 2: Restoring snapshot to staging DB..."
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier staging-db \
  --db-snapshot-identifier staging-snapshot-$(date +%Y%m%d-%H%M%S)

# Wait for restore to complete
aws rds wait db-instance-available --db-instance-identifier staging-db

log "Database restored successfully"

# Step 3: Run PII masking script
log "Step 3: Running PII masking script..."
psql -h staging-db.abc123.us-east-1.rds.amazonaws.com -U admin -d mydb -f mask-pii.sql

if [ $? -ne 0 ]; then
  log "ERROR: PII masking failed"
  notify_slack "❌ Staging refresh FAILED at PII masking step"
  exit 1
fi

log "PII masking completed"

# Step 4: Validate schema and data integrity
log "Step 4: Validating schema and data integrity..."
psql -h staging-db.abc123.us-east-1.rds.amazonaws.com -U admin -d mydb -c "
  SELECT COUNT(*) FROM users;
  SELECT COUNT(*) FROM orders;
  SELECT pg_database_size('mydb');
" > /tmp/db-validation.txt

# Check if user count is reasonable (should be > 1000)
USER_COUNT=$(psql -h staging-db.abc123.us-east-1.rds.amazonaws.com -U admin -d mydb -t -c "SELECT COUNT(*) FROM users;")
if [ "$USER_COUNT" -lt 1000 ]; then
  log "ERROR: User count too low ($USER_COUNT), expected > 1000"
  notify_slack "❌ Staging refresh FAILED at validation step (user count: $USER_COUNT)"
  exit 1
fi

log "Schema validation passed"

# Step 5: Run smoke test suite
log "Step 5: Running smoke tests..."
npm run test:smoke -- --env=staging

if [ $? -ne 0 ]; then
  log "ERROR: Smoke tests failed"
  notify_slack "❌ Staging refresh FAILED at smoke test step"
  exit 1
fi

log "Smoke tests passed"

# Step 6: Mark environment as READY
log "Step 6: Marking staging environment as READY..."
kubectl create configmap staging-status --from-literal=status=READY --dry-run=client -o yaml | kubectl apply -f -

log "Staging environment refresh COMPLETE"
notify_slack "✅ Staging refresh COMPLETE - Environment is READY for testing"

# Cleanup old snapshots (keep last 7 days)
aws rds describe-db-snapshots --query "DBSnapshots[?SnapshotCreateTime<='$(date -d '7 days ago' --iso-8601)'].DBSnapshotIdentifier" --output text | \
  xargs -I {} aws rds delete-db-snapshot --db-snapshot-identifier {}

log "Old snapshots cleaned up"
```

**Rollback Procedure** (If Refresh Fails):
```bash
#!/bin/bash
# rollback-staging.sh - Restore previous snapshot

PREVIOUS_SNAPSHOT=$(aws rds describe-db-snapshots \
  --query "DBSnapshots | sort_by(@, &SnapshotCreateTime) | [-2].DBSnapshotIdentifier" \
  --output text)

echo "Rolling back to previous snapshot: $PREVIOUS_SNAPSHOT"
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier staging-db \
  --db-snapshot-identifier "$PREVIOUS_SNAPSHOT"

notify_slack "⚠️ Staging environment rolled back to $PREVIOUS_SNAPSHOT"
```

### CI/CD Integration
- **On Pull Request**: Run all unit tests, integration tests, and a "smoke test" suite of critical E2E tests. The PR cannot be merged if any of these tests fail.
- **On Merge to Main (Pre-Deployment)**: Run the full E2E test suite against the staging environment.
- **Post-Deployment**: Run the smoke test suite against the production environment to verify the deployment was successful.

### Performance Testing Goals
- **Load Testing**: Use JMeter/K6 to determine the maximum requests per second (RPS) the system can handle before the p99 latency exceeds 500ms or the error rate exceeds 1%.
- **Stress Testing**: Identify the breaking point of the system and ensure it recovers gracefully after the load is removed.
- **Soak Testing**: Run a sustained load over several hours to identify memory leaks or performance degradation over time.

### Security Testing Checklist
- **Focus**: Test for common vulnerabilities from the OWASP Top 10.
- **Authentication/Authorization**: Write tests to ensure that unauthenticated users cannot access protected endpoints and that users cannot access data belonging to other users.
- **Injection**: Write tests that attempt basic SQL or command injection in input fields.
- **Dependency Scanning**: Integrate a tool like `npm audit` or Snyk into the CI pipeline to check for vulnerable dependencies.

### Exploratory Testing
- Allocate 10% of testing time to unscripted, exploratory testing. Focus on user-centric flows and attempt to use the application in unexpected ways. Document any bugs found in the standard bug report format.

## Advanced Testing Strategies

### Visual Regression Testing
- **Tools**: Integrate a tool like Percy or Applitools into the CI pipeline.
- **Process**: Take screenshots of key components and pages during the E2E test run. The pipeline should pause for human approval if any visual diffs are detected. Once approved, the new screenshots become the baseline.

### Accessibility Testing (A11y)
- **Automated**: Integrate `axe-core` with the Cypress/Playwright E2E test suite. The build should fail if there are any violations with a severity of "critical" or "serious".
- **Manual**: Perform quarterly manual audits of critical user flows using a screen reader (NVDA or JAWS) and keyboard-only navigation.

### Contract Testing
- **Use Case**: Essential for microservices architectures to ensure that services can communicate with each other. It verifies that API contracts between a client (consumer) and a server (provider) are not broken.
- **Tools**: Use a tool like Pact.
- **Process**:
  1. **Consumer-side**: The consumer's test suite generates a contract file (`pact file`) that defines the expected requests and the minimal expected responses.
  2. **Provider-side**: The provider verifies the contract against its own API to ensure it can fulfill the consumer's expectations. This is done without needing to run the actual consumer.
  3. **CI/CD Integration**: This verification step is integrated into the provider's CI pipeline. A failure indicates a breaking change, preventing deployment.

### Mutation Testing
- **Use Case**: To assess the quality of your existing test suite, particularly unit tests. It helps answer the question: "Are my tests actually effective at catching bugs?"
- **Tools**: Use a library like Stryker (for JavaScript/TypeScript) or PITest (for Java).
- **Process**:
  1. **Mutant Generation**: The tool automatically creates small, deliberate modifications ("mutants") in your source code (e.g., changing `a + b` to `a - b`, or `>` to `<`).
  2. **Test Execution**: It then runs your test suite against each mutant.
  3. **Analysis**:
     - If a test fails, the mutant is "killed" (good). This means your tests detected the change.
     - If all tests pass, the mutant "survives" (bad). This reveals a weakness in your test suite.
  4. **Reporting**: The tool reports a "Mutation Score," which is the percentage of killed mutants. The goal is to achieve a high score, indicating a robust and effective test suite.

### Flaky Test Quarantine Procedure ⭐ NEW

**Problem**: Flaky tests block CI/CD pipeline, causing lost productivity (10 engineers × 30 min/day = 50 hours/week wasted).

**Solution**: Automatically quarantine flaky tests so they run but don't block PRs.

**Quarantine Criteria**:
A test is quarantined if:
- **Pass rate < 95%** over the last 7 days, OR
- **2+ consecutive failures** within 24 hours (where code didn't change)

**Implementation**:

1. **Track Test Results in Database**:
```javascript
// test-result-tracker.js
const { PrismaClient } = require('@prisma/client');
const prisma = new PrismaClient();

async function recordTestResult(testName, status, duration, commit) {
  await prisma.testResult.create({
    data: {
      testName,
      status,  // 'passed' or 'failed'
      duration,
      commit,
      timestamp: new Date(),
    },
  });
}

// After each test run
afterEach(async function() {
  await recordTestResult(
    this.currentTest.title,
    this.currentTest.state,
    this.currentTest.duration,
    process.env.COMMIT_SHA
  );
});
```

2. **Calculate Flaky Score (Daily Cron Job)**:
```javascript
// calculate-flaky-score.js
async function identifyFlakyTests() {
  const sevenDaysAgo = new Date(Date.now() - 7 * 24 * 60 * 60 * 1000);

  // Get all tests with < 95% pass rate
  const flakyTests = await prisma.$queryRaw`
    SELECT
      test_name,
      COUNT(*) FILTER (WHERE status = 'passed') * 100.0 / COUNT(*) AS pass_rate,
      COUNT(*) AS total_runs
    FROM test_results
    WHERE timestamp >= ${sevenDaysAgo}
    GROUP BY test_name
    HAVING (COUNT(*) FILTER (WHERE status = 'passed') * 100.0 / COUNT(*)) < 95
       AND COUNT(*) >= 5  -- Minimum 5 runs to be statistically valid
  `;

  // Mark as quarantined
  for (const test of flakyTests) {
    await prisma.flakyTest.upsert({
      where: { testName: test.test_name },
      update: {
        passRate: test.pass_rate,
        quarantinedAt: new Date(),
      },
      create: {
        testName: test.test_name,
        passRate: test.pass_rate,
        quarantinedAt: new Date(),
      },
    });

    console.log(`Quarantined: ${test.test_name} (pass rate: ${test.pass_rate.toFixed(1)}%)`);
  }
}

// Run daily at 6 AM
cron.schedule('0 6 * * *', identifyFlakyTests);
```

3. **Skip Quarantined Tests in CI** (But Still Run in Reporting Mode):
```javascript
// jest.config.js
const { PrismaClient } = require('@prisma/client');
const prisma = new PrismaClient();

let quarantinedTests = [];

// Load quarantined tests before test run
beforeAll(async () => {
  const results = await prisma.flakyTest.findMany({
    where: { quarantinedAt: { not: null } },
  });
  quarantinedTests = results.map(r => r.testName);
});

// Skip quarantined tests in CI, but run locally
beforeEach(function() {
  const isCI = process.env.CI === 'true';
  const isQuarantined = quarantinedTests.includes(this.currentTest.title);

  if (isCI && isQuarantined) {
    this.skip();  // Don't block CI/CD pipeline
    console.log(`⚠️  QUARANTINED: ${this.currentTest.title} (skipped in CI)`);
  }
});
```

4. **Weekly Quarantine Report** (Slack/Email):
```javascript
// send-flaky-report.js
async function sendWeeklyFlakyReport() {
  const quarantined = await prisma.flakyTest.findMany({
    where: { quarantinedAt: { not: null } },
    orderBy: { passRate: 'asc' },
  });

  if (quarantined.length === 0) {
    return;  // No flaky tests, all good!
  }

  const report = `
📊 Weekly Flaky Test Report

Currently Quarantined: ${quarantined.length} tests

${quarantined.map(t =>
  `- ${t.testName} (pass rate: ${t.passRate.toFixed(1)}%, quarantined ${Math.floor((Date.now() - t.quarantinedAt) / (24 * 60 * 60 * 1000))} days ago)`
).join('\n')}

⚠️ Action Required: Fix or delete within 5 business days
  `;

  await fetch(SLACK_WEBHOOK, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ text: report }),
  });
}

// Run every Monday at 9 AM
cron.schedule('0 9 * * 1', sendWeeklyFlakyReport);
```

5. **Remediation SLA**:
- **Goal**: Fix or delete quarantined tests within **5 business days**
- **After 5 days**: Auto-create Jira ticket assigned to test owner
- **After 10 days**: Test is auto-deleted from suite (better to delete than keep flaky)

**Root Cause Classification** (Add to Jira Ticket):
- **Timing Issue**: Race condition, missing `waitFor`, animation delays
- **Network Issue**: External API flakiness, DNS resolution
- **Data Dependency**: Test depends on shared state or external data
- **Infrastructure**: CI runner resource constraints, timeouts

## Common Pitfalls to Avoid

1. **Inverted Test Pyramid** - Too many E2E tests leads to slow, brittle CI builds
   - **Solution**: Enforce 70:20:10 ratio (unit:integration:E2E)

2. **Flaky Tests Blocking PRs** - One unreliable test blocks entire team
   - **Solution**: Auto-quarantine tests with <95% pass rate

3. **PII in Test Environments** - GDPR violations from real customer data
   - **Solution**: Automated PII masking with Faker.js or pg_anonymize

4. **Manual Environment Refresh** - Weekend outages from failed manual refresh
   - **Solution**: Nightly automated refresh with validation and rollback

5. **No Test Data Isolation** - Tests fail due to shared state
   - **Solution**: Each test creates its own data, cleans up after

6. **Skipping Smoke Tests Post-Deploy** - Deploy succeeded, but app is broken
   - **Solution**: Always run smoke tests after production deployment

7. **No Mutation Testing** - 100% code coverage but tests don't catch bugs
   - **Solution**: Use Stryker to validate test suite effectiveness

8. **Ignoring Accessibility** - App is unusable for screen reader users
   - **Solution**: Integrate axe-core into CI, fail build on critical violations
