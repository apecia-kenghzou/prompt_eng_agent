## ⚠️ CRITICAL: Database Transactions & Concurrency

### Race Condition Prevention

**Problem**: Concurrent requests modifying the same resource can cause data corruption.

**Example (WRONG - Race Condition):**
```javascript
// ❌ NEVER DO THIS - Race condition causes double withdrawal
async function withdraw(accountId, amount) {
  const account = await Account.findById(accountId)

  // RACE: Another request could modify balance here
  if (account.balance >= amount) {
    account.balance -= amount
    await account.save()  // May overdraft if concurrent withdrawal
  }
}
```

**Solution 1: Pessimistic Locking (SELECT FOR UPDATE)**
```javascript
// ✅ Correct - Lock row until transaction completes
async function withdraw(accountId, amount) {
  const transaction = await sequelize.transaction()

  try {
    // Lock the row - other transactions must wait
    const account = await Account.findById(accountId, {
      lock: transaction.LOCK.UPDATE,
      transaction
    })

    if (account.balance < amount) {
      throw new Error('Insufficient funds')
    }

    account.balance -= amount
    await account.save({ transaction })
    await transaction.commit()
  } catch (error) {
    await transaction.rollback()
    throw error
  }
}
```

**Solution 2: Optimistic Locking (Version Field)**
```javascript
// ✅ Correct - Detect concurrent modifications
async function updateUser(userId, updates) {
  const user = await User.findById(userId) // version = 5

  // Apply updates
  Object.assign(user, updates)

  // Only save if version hasn't changed
  const updated = await User.update(
    { ...updates, version: user.version + 1 },
    {
      where: {
        id: userId,
        version: user.version  // Only update if version still 5
      }
    }
  )

  if (updated === 0) {
    throw new Error('Concurrent modification detected - retry')
  }
}
```

### Transaction Best Practices

**Multi-Step Operations:**
```javascript
async function transferMoney(fromId, toId, amount) {
  const transaction = await sequelize.transaction({
    isolationLevel: Transaction.ISOLATION_LEVELS.READ_COMMITTED
  })

  try {
    // Step 1: Debit source account (with lock)
    const from = await Account.findById(fromId, {
      lock: transaction.LOCK.UPDATE,
      transaction
    })

    if (from.balance < amount) {
      throw new Error('Insufficient funds')
    }

    from.balance -= amount
    await from.save({ transaction })

    // Step 2: Credit destination account (with lock)
    const to = await Account.findById(toId, {
      lock: transaction.LOCK.UPDATE,
      transaction
    })

    to.balance += amount
    await to.save({ transaction })

    // Step 3: Create audit log
    await TransactionLog.create({
      from: fromId,
      to: toId,
      amount,
      timestamp: new Date()
    }, { transaction })

    await transaction.commit()
  } catch (error) {
    await transaction.rollback()
    throw error
  }
}
```

**Isolation Levels:**
- **READ_COMMITTED** (default): Prevents dirty reads
- **REPEATABLE_READ**: Prevents non-repeatable reads (use for financial transactions)
- **SERIALIZABLE**: Full isolation (slowest, use sparingly)

**Deadlock Handling:**
```javascript
async function retryOnDeadlock(operation, maxRetries = 3) {
  for (let i = 0; i < maxRetries; i++) {
    try {
      return await operation()
    } catch (error) {
      // PostgreSQL deadlock error code
      if (error.code === '40P01' && i < maxRetries - 1) {
        await sleep(Math.pow(2, i) * 100) // Exponential backoff
        continue
      }
      throw error
    }
  }
}
```

## ⚠️ CRITICAL: API Idempotency

### Idempotency Keys (Stripe Pattern)

**Problem**: Users clicking "Pay" twice or network retries cause duplicate operations.

**Implementation:**
```javascript
const redis = require('redis').createClient()

app.post('/api/payments', async (req, res) => {
  const idempotencyKey = req.headers['idempotency-key']

  if (!idempotencyKey) {
    return res.status(400).json({
      error: { code: 'MISSING_IDEMPOTENCY_KEY', message: 'Required header' }
    })
  }

  // Check if we've seen this key before
  const cached = await redis.get(`idempotency:${idempotencyKey}`)

  if (cached) {
    // Return cached response (request was duplicate)
    return res.status(200).json(JSON.parse(cached))
  }

  try {
    // Process payment (only once)
    const payment = await processPayment(req.body)

    const response = { success: true, payment }

    // Cache response for 24 hours
    await redis.setex(
      `idempotency:${idempotencyKey}`,
      86400,
      JSON.stringify(response)
    )

    return res.status(201).json(response)
  } catch (error) {
    // Don't cache errors - allow retry
    throw error
  }
})
```

**Client Implementation:**
```javascript
// Frontend generates UUID for each unique operation
import { v4 as uuidv4 } from 'uuid'

async function submitPayment(paymentData) {
  const idempotencyKey = uuidv4() // Generated once per user action

  const response = await fetch('/api/payments', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Idempotency-Key': idempotencyKey
    },
    body: JSON.stringify(paymentData)
  })

  // Safe to retry with same key if network fails
  return response.json()
}
```

**When to Use Idempotency:**
- POST/PUT/DELETE requests (state-changing operations)
- Payment processing
- Order creation
- Account modifications
- Any operation that can't safely be repeated

## ⚠️ CRITICAL: Circuit Breakers & Backpressure

### Circuit Breaker Pattern

**Problem**: Slow downstream service exhausts thread pool, causes cascading failure.

**Implementation (Node.js with Opossum):**
```javascript
const CircuitBreaker = require('opossum')

// Configure circuit breaker
const breaker = new CircuitBreaker(callDownstreamService, {
  timeout: 3000,          // Fail if call takes > 3s
  errorThresholdPercentage: 50,  // Open circuit if 50% fail
  resetTimeout: 30000     // Try again after 30s
})

// Monitor circuit state
breaker.on('open', () => {
  logger.error('Circuit breaker opened - downstream service failing')
  metrics.increment('circuit_breaker.opened')
})

breaker.on('halfOpen', () => {
  logger.info('Circuit breaker half-open - testing downstream')
})

breaker.on('close', () => {
  logger.info('Circuit breaker closed - downstream recovered')
})

// Fallback when circuit is open
breaker.fallback(() => {
  return { cached: true, data: getCachedData() }
})

// Use circuit breaker
app.get('/api/data', async (req, res) => {
  try {
    const data = await breaker.fire(req.params)
    res.json(data)
  } catch (error) {
    if (error.message === 'Breaker is open') {
      res.status(503).json({
        error: { code: 'SERVICE_UNAVAILABLE', message: 'Try again later' }
      })
    } else {
      throw error
    }
  }
})

async function callDownstreamService(params) {
  const controller = new AbortController()
  const timeout = setTimeout(() => controller.abort(), 3000)

  try {
    const response = await fetch('https://api.example.com/data', {
      signal: controller.signal
    })
    return await response.json()
  } finally {
    clearTimeout(timeout)
  }
}
```

### Backpressure & Rate Limiting

**Service-to-Service Rate Limiting:**
```javascript
const Bottleneck = require('bottleneck')

// Limit concurrent calls to downstream service
const limiter = new Bottleneck({
  maxConcurrent: 10,   // Max 10 simultaneous calls
  minTime: 100         // Min 100ms between calls
})

async function callDownstream(data) {
  return limiter.schedule(() => fetchFromService(data))
}
```

**Bulkhead Pattern (Isolate Resources):**
```javascript
// Separate thread pools per dependency
const paymentLimiter = new Bottleneck({ maxConcurrent: 5 })
const emailLimiter = new Bottleneck({ maxConcurrent: 20 })
const dbLimiter = new Bottleneck({ maxConcurrent: 50 })

// If email service is slow, doesn't affect payments or DB
```

## ⚠️ CRITICAL: Connection Pool Management

### Database Connection Pooling

**Configuration:**
```javascript
const { Pool } = require('pg')

const pool = new Pool({
  host: process.env.DB_HOST,
  port: process.env.DB_PORT,
  database: process.env.DB_NAME,
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,

  // Pool configuration
  min: 2,              // Keep min 2 connections open
  max: 10,             // Max 10 connections
  idleTimeoutMillis: 30000,   // Close idle connections after 30s
  connectionTimeoutMillis: 5000,  // Fail if can't get connection in 5s

  // Statement timeout (prevent long-running queries)
  statement_timeout: 10000  // Kill queries after 10s
})

// Monitor pool health
pool.on('error', (err) => {
  logger.error('Database pool error', { error: err })
  metrics.increment('db.pool.error')
})

pool.on('connect', () => {
  metrics.gauge('db.pool.connections', pool.totalCount)
})

pool.on('remove', () => {
  metrics.gauge('db.pool.connections', pool.totalCount)
})
```

**Prevent Connection Leaks:**
```javascript
// ❌ WRONG - Leaks connection on error
async function queryUser(id) {
  const client = await pool.connect()
  const result = await client.query('SELECT * FROM users WHERE id = $1', [id])
  // If error thrown above, connection never released!
  client.release()
  return result.rows[0]
}

// ✅ CORRECT - Always release
async function queryUser(id) {
  const client = await pool.connect()

  try {
    const result = await client.query('SELECT * FROM users WHERE id = $1', [id])
    return result.rows[0]
  } finally {
    client.release()  // Always executes
  }
}

// ✅ BETTER - Use pool.query (auto-release)
async function queryUser(id) {
  const result = await pool.query('SELECT * FROM users WHERE id = $1', [id])
  return result.rows[0]
}
```

**Pool Sizing Formula:**
```
Optimal pool size = (CPU cores * 2) + 1

For 4-core server:
  min: 2
  max: 9 (4 * 2 + 1)

Why: Database is I/O bound, not CPU bound.
More connections = more context switching overhead.
```

**Monitoring:**
```javascript
// Expose pool metrics
app.get('/metrics', (req, res) => {
  res.json({
    db_pool_total: pool.totalCount,
    db_pool_idle: pool.idleCount,
    db_pool_waiting: pool.waitingCount
  })
})

// Alert if waiting connections > 5 for 1 minute
```

## Production-Ready Standards

### API Security
- **Authentication**: Implement OAuth 2.0 or JWTs for stateless authentication. **Use the RS256 signing algorithm for all JWTs.**
- **Authorization**: Enforce Role-Based Access Control (RBAC) on all endpoints.
- **Input Validation**: Sanitize all inputs to prevent SQL injection, NoSQL injection, and XSS.
- **Secrets Management**: Use environment variables for local development, but integrate with a secrets manager (e.g., HashiCorp Vault, AWS/GCP Secrets Manager) for staging and production environments.

### Error Handling Architecture
- **Standardized Error Response**: All API errors must return a JSON object: `{"error": {"code": "ERROR_CODE", "message": "Descriptive message"}}`.
- **HTTP Status Codes**: Use appropriate codes (400 for validation errors, 401/403 for auth, 404 for not found, 500 for server errors).
- **Error Logging**: Log all 5xx errors as `{"level": "error", "timestamp": "...", "message": "...", "stackTrace": "..."}`.
- **Client vs. Server Errors**: Client errors (4xx) should return a clear message; Server errors (5xx) should log detailed stack traces but return a generic message to the user.

### Testing Strategy
- **Unit Tests (70% coverage)**: Test individual functions, classes, and modules in isolation. Use Jest (Node.js) or Pytest (Python). Mocks should be used for external dependencies (databases, APIs).
- **Integration Tests (20% coverage)**: Test service-level interactions, such as API endpoints connecting to a test database. Use Supertest (Node.js) or FastAPI's TestClient (Python).
- **E2E & Load Tests (10% coverage)**: Test critical user flows from end-to-end. Use K6 or JMeter for load testing critical endpoints to ensure they meet performance targets under stress.

### Observability
- **Structured Logging**: All log output must be in JSON format. Include a `correlation_id` in logs to trace a request through the system.
- **Metrics**: Expose a `/metrics` endpoint formatted for Prometheus. Key metrics must include: `http_requests_total`, `http_requests_duration_seconds`, `http_requests_errors_total`, `db_pool_connections`, `circuit_breaker_state`.
- **Health Checks**: The `/health` endpoint must check connectivity to the database and other critical downstream services.

### Configuration Management
- **Environment Variables**: No hardcoded secrets or configuration. All configuration must be loaded from environment variables.
- **Example `.env` File**: Provide a `.env.example` file documenting all required variables.
- **Multi-Environment**: Design must support distinct configurations for `development`, `staging`, and `production`.

### Caching Patterns
- **Cache-Aside for Reads**: For read-heavy, non-critical data, the application should first check the Redis cache. If a cache miss occurs, query the database and populate the cache.
- **What to Cache**: User sessions, public configuration data, results of expensive queries (>200ms).
- **Cache Invalidation**: Use TTL-based invalidation (e.g., 5-10 minutes) for data that can be slightly stale.

### Database Migrations
- Use a migration tool like `node-pg-migrate` (Node.js) or `Alembic` (Python).
- All schema changes must be committed as new, reversible migration scripts.
- **Zero-Downtime Migrations**: For column renames or deletions, use the expand-contract pattern:
  1. Add new column (backward compatible)
  2. Deploy code that writes to both columns
  3. Backfill data
  4. Deploy code that reads from new column
  5. Drop old column in next release

## Common Pitfalls to Avoid

1. ❌ No transaction for multi-step operations → data corruption
2. ❌ No idempotency keys on POST/PUT/DELETE → duplicate charges
3. ❌ No circuit breaker for downstream calls → cascading failures
4. ❌ No connection pool limits → database exhaustion
5. ❌ No SELECT FOR UPDATE on concurrent writes → race conditions
6. ❌ No timeout on external API calls → thread pool exhaustion
7. ❌ Optimistic locking without retry logic → silent failures
8. ❌ Caching errors in idempotency layer → permanent failures
9. ❌ Not releasing connections in finally block → connection leaks
10. ❌ Using SERIALIZABLE isolation everywhere → performance death
