## MLOps Project Workflow

### 1. Problem Definition
- **Business Objective**: Clearly define the business problem to be solved (e.g., "Predict customer churn").
- **ML Formulation**: Frame the problem as an ML task (e.g., "Binary classification to predict a `will_churn` flag").
- **Success Criteria**: Define the business and technical success metrics (e.g., "Achieve a model F1 score > 0.85" and "Reduce churn by a projected 5%").

### 2. Data Preprocessing & Feature Engineering
- **Data Splitting**: The very first step must be to split the raw data into training and testing sets.
- **Preprocessing Pipeline**: All preprocessing steps (scaling, encoding, imputation) must be fitted on the **training set only**. The fitted pipeline is then used to transform both the training and testing sets. This prevents data leakage.
- **Feature Engineering**: ...

### 3. Experiment Tracking & Model Training
- **Experiment Tracking**: Use MLflow to log all experiments. For each run, log:
  - Git commit hash
  - Model parameters and hyperparameters
  - Evaluation metrics (Accuracy, F1-Score, etc.)
  - The trained model artifact itself.
- **Model Selection**: ...
- **Hyperparameter Tuning**: ...

### 4. Deployment & Serving
- **Model Registry**: The best-performing, validated model must be registered in the MLflow Model Registry with a version number.
- **Deployment Pipeline**: Create an automated pipeline (e.g., using Kubeflow or GitHub Actions) that takes a model version from the registry, builds a container, and deploys it to a target environment (e.g., a Kubernetes cluster).
- **API Server**: The API must include a `/health` endpoint and a `/metadata` endpoint that returns the model version and training date.

### 5. Post-Deployment Monitoring
- **Model Monitoring**: Implement a monitoring service that tracks the live model's performance and watches for data drift and concept drift. Key metrics to monitor include the distribution of input features and the distribution of the model's prediction scores.
- **Retraining Strategy**: Define a clear trigger for retraining the model (e.g., "Retrain the model quarterly or whenever the live F1 score drops by 10% from its training value"). The retraining process should be automated.
