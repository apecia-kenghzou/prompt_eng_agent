#### Feature Store Integration ⭐ NEW

**Problem**: Without a feature store, features are computed differently in training (Python/SQL) and serving (API/Spark), causing **training-serving skew** (42% of ML incidents at Uber).

**Solution**: Define features once in a feature store, use the same code for training and serving.

**Tools**:
- **Feast** (open source, used by Airbnb/Netflix)
- **Tecton** (commercial, built by ex-Uber ML team)
- **AWS SageMaker Feature Store**
- **Databricks Feature Store**

**Feature Store Workflow**:

1. **Define Features** (once, in code):
```python
# src/features/user_features.py
from feast import Feature, FeatureView, Field, FileSource
from feast.types import Float64, Int64
from datetime import timedelta

# Define batch data source
user_orders_source = FileSource(
    path="/data/user_orders.parquet",
    timestamp_field="event_timestamp",
)

# Define feature view
user_features = FeatureView(
    name="user_features",
    entities=["user_id"],
    ttl=timedelta(days=30),  # Features valid for 30 days
    schema=[
        Field(name="days_since_last_order", dtype=Int64),
        Field(name="avg_order_value_30d", dtype=Float64),
        Field(name="total_orders", dtype=Int64),
        Field(name="is_premium_member", dtype=Int64),
    ],
    online=True,  # Enable online serving (Redis)
    source=user_orders_source,
)
```

2. **Training**: Fetch Historical Features (Point-in-Time Correct):
```python
# Training: Get features "as of" each training example timestamp
from feast import FeatureStore

store = FeatureStore(repo_path=".")

# Entity dataframe with labels and timestamps
training_df = pd.DataFrame({
    'user_id': [1, 2, 3],
    'event_timestamp': ['2023-01-01', '2023-01-02', '2023-01-03'],
    'will_churn': [0, 1, 0],  # Labels
})

# Fetch features (point-in-time correct, no future leakage)
training_features = store.get_historical_features(
    entity_df=training_df,
    features=[
        "user_features:days_since_last_order",
        "user_features:avg_order_value_30d",
        "user_features:total_orders",
        "user_features:is_premium_member",
    ],
).to_df()

# Result: Features computed as they existed at event_timestamp (no leakage)
```

3. **Serving**: Fetch Online Features (Low Latency from Redis):
```python
# Serving: Real-time prediction API
from feast import FeatureStore

store = FeatureStore(repo_path=".")

# Fetch latest features for a user (sub-10ms latency from Redis)
features = store.get_online_features(
    features=[
        "user_features:days_since_last_order",
        "user_features:avg_order_value_30d",
        "user_features:total_orders",
        "user_features:is_premium_member",
    ],
    entity_rows=[{"user_id": 12345}],
).to_dict()

# Make prediction
prediction = model.predict([list(features.values())])
```

**Benefits**:
- ✅ **Single Source of Truth**: Features defined once, used everywhere
- ✅ **Zero Training-Serving Skew**: Exact same code path
- ✅ **Point-in-Time Correctness**: No future leakage in training data
- ✅ **Feature Reuse**: 10 models can share `user_features`, defined once

**When to Use Feature Store**:
- **Required**: For production models with >5 features or >2 models sharing features
- **Optional**: For one-off experiments or models with <5 features

#### Fairness & Bias Testing ⭐ NEW

**Requirement**: For models used in regulated domains (hiring, lending, insurance, healthcare), you MUST test for bias on protected attributes.

**Legal Context**:
- **EEOC (US)**: Employment decisions cannot discriminate based on race, gender, age
- **Fair Housing Act (US)**: Lending decisions cannot discriminate based on race, religion
- **GDPR (EU)**: Right to explanation for automated decisions

**Fairness Metrics**:

1. **Demographic Parity (Statistical Parity)**
   - **Definition**: The model should predict positive outcomes at the same rate across all groups.
   - **Formula**: P(ŷ=1 | A=0) ≈ P(ŷ=1 | A=1)
   - **Example**: Loan approval rate should be similar for men and women.
   - **Threshold**: Difference should be <5% (EEOC 80% rule: min/max ratio ≥ 0.8)

2. **Equalized Odds (Equal Opportunity)**
   - **Definition**: The model should have the same True Positive Rate (TPR) and False Positive Rate (FPR) across all groups.
   - **Formula**: TPR(A=0) ≈ TPR(A=1) AND FPR(A=0) ≈ FPR(A=1)
   - **Example**: If a qualified woman applies, she should have the same approval probability as a qualified man.
   - **Threshold**: Difference in TPR and FPR should be <5%

3. **Predictive Parity (Precision Parity)**
   - **Definition**: Among those predicted positive, the actual positive rate should be the same across groups.
   - **Formula**: PPV(A=0) ≈ PPV(A=1)
   - **Example**: Among approved loans, default rate should be similar for all races.
   - **Threshold**: Difference should be <5%

**Implementation** (using Fairlearn library):
```python
# src/fairness/fairness_metrics.py
from fairlearn.metrics import MetricFrame, selection_rate, demographic_parity_difference
from sklearn.metrics import accuracy_score, precision_score, recall_score

# Compute fairness metrics
y_true = test_df['approved']
y_pred = model.predict(X_test)
sensitive_features = test_df['gender']  # Protected attribute

# Metric frame: Compute metrics by group
mf = MetricFrame(
    metrics={
        'accuracy': accuracy_score,
        'precision': precision_score,
        'recall': recall_score,
        'selection_rate': selection_rate,  # P(ŷ=1)
    },
    y_true=y_true,
    y_pred=y_pred,
    sensitive_features=sensitive_features,
)

print(mf.by_group)
# Output:
#          accuracy  precision  recall  selection_rate
# gender
# Male       0.85      0.80      0.75    0.60
# Female     0.82      0.75      0.70    0.45  ⚠️ 15% difference

# Demographic Parity Difference
dpd = demographic_parity_difference(
    y_true=y_true,
    y_pred=y_pred,
    sensitive_features=sensitive_features,
)
print(f"Demographic Parity Difference: {dpd:.3f}")  # 0.15 (Male 60% - Female 45%)

# Fairness Check
if abs(dpd) > 0.05:
    print("⚠️ FAIRNESS VIOLATION: Demographic parity difference > 5%")
    print("   Model may discriminate against protected group.")
    print("   Consider: re-weighting, adversarial debiasing, or fairness constraints.")

# Log fairness metrics to MLflow
import mlflow
mlflow.log_metric("demographic_parity_diff", dpd)
mlflow.log_metric("selection_rate_male", 0.60)
mlflow.log_metric("selection_rate_female", 0.45)
```

#### A/B Testing & Gradual Rollout Strategy ⭐ NEW

**Problem**: Deploying a new model to 100% of users is risky. Offline metrics don't always predict online performance. (Netflix lost $10M+ from a bad recommendation algo deployed to 100% of users without A/B test.)

**Solution**: Gradual rollout with validation at each step.

**Deployment Progression**:

1. **Shadow Mode** (2 weeks):
   - Run new model alongside old model
   - Log predictions from both, but only serve old model's predictions to users
   - Compare predictions offline (correlation, disagreement rate)
   - **Goal**: Sanity check that new model behaves reasonably

```python
# Shadow mode implementation
@app.post("/predict")
async def predict(features: dict):
    # Serve old model (production)
    old_prediction = old_model.predict([features])

    # Run new model in shadow (don't serve to user)
    new_prediction = new_model.predict([features])

    # Log comparison for offline analysis
    log_predictions({
        'user_id': features['user_id'],
        'old_prediction': old_prediction,
        'new_prediction': new_prediction,
        'timestamp': datetime.now(),
    })

    # Only serve old model's prediction
    return {"prediction": old_prediction}
```

2. **Canary 5%** (3 days):
   - Serve new model to 5% of users (based on user_id hash)
   - Monitor business metrics: conversion rate, engagement, revenue
   - Monitor ML metrics: prediction distribution, latency, error rate
   - **Rollback** if any metric degrades >5%

```python
# A/B test implementation
@app.post("/predict")
async def predict(features: dict):
    user_id = features['user_id']

    # Assign to variant based on user_id hash (stable assignment)
    if hash(user_id) % 100 < 5:  # 5% of users
        prediction = new_model.predict([features])  # Variant B
        variant = 'new_model'
    else:
        prediction = old_model.predict([features])  # Control A
        variant = 'old_model'

    # Log for A/B analysis
    log_prediction({
        'user_id': user_id,
        'variant': variant,
        'prediction': prediction,
        'timestamp': datetime.now(),
    })

    return {"prediction": prediction, "variant": variant}
```

3. **Canary 25%** (3 days):
   - If 5% canary passed, increase to 25% of users
   - Continue monitoring

4. **Canary 50%** (7 days):
   - If 25% canary passed, increase to 50% of users

5. **Full Rollout 100%**:
   - Only if all canary stages passed
   - New model becomes the default
   - Old model kept for rollback

### 6. Post-Deployment Monitoring

#### Data Drift Detection ⭐ NEW

**Problem**: Models degrade over time as data distributions shift. Without automated drift detection, you catch this weeks/months late. (Zillow lost $569M from undetected concept drift during COVID.)

**Solution**: Automated drift detection with statistical tests and alerting.

**Drift Types**:
1. **Data Drift (Covariate Shift)**: Input distribution changes, P(X) changes
   - Example: User age distribution shifts from 25-35 → 45-55
2. **Concept Drift**: Relationship between inputs and output changes, P(Y|X) changes
   - Example: During COVID, relationship between "location" and "demand" changed completely

**Drift Detection Metrics**:

1. **Population Stability Index (PSI)**:
   - Measures distribution shift between training and production data
   - **PSI < 0.1**: No significant shift ✅
   - **PSI 0.1-0.2**: Moderate shift (investigate) ⚠️
   - **PSI > 0.2**: Significant shift (retrain model) ❌

```python
# src/monitoring/drift_detection.py
import numpy as np

def calculate_psi(expected, actual, bins=10):
    """
    Calculate Population Stability Index (PSI)

    expected: Training data feature values
    actual: Production data feature values (last 7 days)
    bins: Number of bins for histogram
    """
    # Create bins based on training data
    breakpoints = np.percentile(expected, np.linspace(0, 100, bins + 1))

    # Calculate percentage in each bin
    expected_percents = np.histogram(expected, bins=breakpoints)[0] / len(expected)
    actual_percents = np.histogram(actual, bins=breakpoints)[0] / len(actual)

    # Avoid division by zero
    expected_percents = np.where(expected_percents == 0, 0.0001, expected_percents)
    actual_percents = np.where(actual_percents == 0, 0.0001, actual_percents)

    # PSI formula
    psi = np.sum((actual_percents - expected_percents) * np.log(actual_percents / expected_percents))

    return psi

# Monitor in production (daily cron job)
for feature in feature_columns:
    psi_score = calculate_psi(
        expected=training_data[feature],
        actual=production_data_last_7_days[feature],
    )

    print(f"{feature}: PSI = {psi_score:.3f}")

    if psi_score > 0.2:
        send_slack_alert(f"🚨 DRIFT DETECTED: {feature} (PSI = {psi_score:.3f})")
        trigger_model_retraining()
```

2. **Kolmogorov-Smirnov (KS) Test**:
   - Statistical test for distribution equality
   - **P-value < 0.05**: Distributions are significantly different (drift detected)


## Common Pitfalls to Avoid

1. **Data Leakage** - Preprocessing before train-test split
   - **Solution**: Split FIRST, then fit preprocessing only on training data

2. **No Fairness Testing** - Deploy biased models (Amazon recruiting, COMPAS)
   - **Solution**: Test demographic parity, equalized odds on protected attributes

3. **Training-Serving Skew** - Features computed differently in training vs serving
   - **Solution**: Use feature store (Feast) for single source of truth

4. **Full Production Rollout** - Bad model deployed to 100% of users
   - **Solution**: Shadow mode → 5% canary → 25% → 50% → 100%

5. **Late Drift Detection** - Catch model degradation after weeks/months
   - **Solution**: Automated PSI/KS test with daily monitoring

6. **No Experiment Tracking** - Can't reproduce winning model
   - **Solution**: MLflow logs all params, metrics, artifacts, git commit

7. **Black Box Models** - Stakeholders reject unexplainable models
   - **Solution**: SHAP required for complex models

8. **No Retraining Strategy** - Models drift indefinitely
   - **Solution**: Automated triggers (drift, performance drop, quarterly)
